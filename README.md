# ICT Laboratory Assistant Bot

Консольное приложение на C++, моделирующее работу информационного бота лаборанта кабинета ИКТ.

## Реализованные модули

### Модуль 1 — Учет рабочего времени

Программа запрашивает количество рабочих дней, ставку и количество часов работы в день. Выполняется расчет недельного рабочего времени и проверка установленной нормы.

### Модуль 2 — Дисциплинарные взыскания

Программа выводит информацию о дисциплинарных последствиях при несанкционированном выносе учебного ноутбука и нарушении учебного процесса.

### Модуль 3 — Протокол реагирования на саботаж

Программа последовательно выводит этапы реагирования на нарушение.

Для имитации работы системы в реальном времени используются задержки `std::this_thread::sleep_for`.

## Компиляция и запуск

Для компиляции:

```bash
g++ main.cpp -o bot -pthread
```

Для запуска:

```bash
./bot
```

## Code Review & Vulnerability Analysis

### 1. Возможность обхода проверки количества рабочих дней

**Описание проблемы:**

В функции проверки рабочего времени условие связано с конкретным значением `days == 5`.

Если пользователь укажет другое количество рабочих дней, например `4`, проверка нормы рабочего времени может быть обойдена.

Пример проблемного ввода:

- количество рабочих дней: 4
- ставка: 0.5
- количество часов в день: 2

В такой ситуации программа может принять данные и продолжить работу, несмотря на несоответствие требуемой норме.

**Потенциальные последствия:**

В реальной системе некорректные сведения о рабочем графике могут быть приняты как правильные. Это может привести к неправильному учету рабочего времени сотрудника и нарушению расписания.

**Предлагаемое решение:**

Необходимо отдельно валидировать количество рабочих дней и не разрешать переход к следующему этапу до ввода допустимого значения.

Например:

```cpp
while (days != 5) {
    cout << "Ошибка! Для данного режима требуется 5 рабочих дней: ";
    cin >> days;
}
```

### 2. Возможность обхода проверки ставки

**Описание проблемы:**

Проверка нормы рабочего времени также зависит от условия `rate == 0.5`.

Если пользователь введет другое значение ставки, например `1.0`, основная проверка может быть обойдена.

Пример проблемного ввода:

- количество рабочих дней: 5
- ставка: 1.0
- количество часов в день: 2

Программа может продолжить работу, хотя данный сценарий предназначен для ставки 0.5.

**Потенциальные последствия:**

Неверное значение ставки может привести к неправильному расчету рабочего времени и формированию недостоверных данных о нагрузке сотрудника.

**Предлагаемое решение:**

Необходимо отдельно проверять ставку и не разрешать продолжение программы, пока пользователь не введет значение 0.5.

```cpp
while (rate != 0.5) {
    cout << "Ошибка! Для данного режима требуется ставка 0.5: ";
    cin >> rate;
}
```

### 3. Отсутствие проверки верхней границы количества часов

**Описание проблемы:**

В исходной реализации ошибка определяется только при условии `dailyHours < 4.0`.

Из-за этого значение больше четырех часов может быть принято программой как корректное.

Пример проблемного ввода:

- количество рабочих дней: 5
- ставка: 0.5
- количество часов в день: 100

Значение 100 часов явно не соответствует требуемой норме 4 часа в день, однако условие `dailyHours < 4.0` для него является ложным, поэтому программа может продолжить работу.

**Потенциальные последствия:**

Система может принять заведомо некорректные сведения о рабочем времени. Это приводит к недостоверному учету нагрузки сотрудника.

**Предлагаемое решение:**

Необходимо требовать точного соответствия установленной норме:

```cpp
while (dailyHours != 4.0) {
    cout << "Ошибка! Требуется установить норму 4 часа в день: ";
    cin >> dailyHours;
}
```

### 4. Жестко заданный номер ноутбука

**Описание проблемы:**

В программе номер ноутбука `17` записан непосредственно в коде.

Из-за этого модуль дисциплинарных взысканий и протокол реагирования фактически работают только с одним заранее заданным номером оборудования.

Например, если нарушение связано с ноутбуком №12, программа все равно выведет информацию о ноутбуке №17.

**Потенциальные последствия:**

Это может привести к неправильной идентификации оборудования, ошибкам при фиксации инцидента и формированию неверной служебной информации.

**Предлагаемое решение:**

Номер ноутбука необходимо хранить в переменной и запрашивать у пользователя:

```cpp
int laptopNumber;

cout << "Введите номер ноутбука: ";
cin >> laptopNumber;

cout << "Инцидент с ноутбуком №" << laptopNumber << endl;
```

---

### 5. Недостаточная проверка диапазона входных данных

**Описание проблемы:**

Программа обнаруживает ввод неправильного типа через `cin`, однако некоторые числовые значения не проверяются на допустимый диапазон.

Например, пользователь может ввести:

- количество рабочих дней: -5
- количество часов в день: -10

Такие значения являются числами, поэтому сам `cin` не считает их ошибкой, хотя для системы учета рабочего времени они некорректны.

**Потенциальные последствия:**

Использование отрицательных или нереалистичных значений может привести к неправильным расчетам рабочего времени и недостоверным результатам.

**Предлагаемое решение:**

После проверки типа данных необходимо дополнительно проверять допустимый диапазон:

```cpp
while (days <= 0 || days > 7) {
    cout << "Количество рабочих дней должно быть от 1 до 7: ";
    cin >> days;
}

while (dailyHours <= 0 || dailyHours > 24) {
    cout << "Количество часов должно быть от 1 до 24: ";
    cin >> dailyHours;
}
```

## Итог Code Review

В ходе анализа были выявлены пять проблем, связанных с валидацией пользовательского ввода и логикой работы программы.

Предложенные исправления позволяют повысить надежность программы без удаления существующей функциональности.

Основная бизнес-логика сохраняется:

- интерактивное меню;
- информационные блоки СРС №1;
- контрольный вопрос;
- учет рабочего времени;
- дисциплинарные взыскания;
- протокол реагирования на саботаж.

Таким образом, исправление обнаруженных проблем соответствует принципу «Don’t throw the baby out with the bathwater»: уязвимости устраняются без нарушения уже работающей логики программы.
